## 2026-04-23: 项目架构选择 Polyrepo

### 背景
- 规划开发多个Agent相关产品
- 产品分为开源基础设施（Built4rag, Built4skill）和商业产品
- 各产品技术栈不同（Python、TS、Go等）
- 单人开发 + AI Agent Team

### 决策
选择 **Polyrepo**：每个产品独立repo

### 决策理由
1. 开源产品需要独立repo建立社区
2. 产品独立 + Docker集成 → Monorepo共享代码优势不明显
3. 单人开发 → 管理成本可控

## 2026-04-23: ParserService vs MinerU API (已决策 → MinerU API)

### 背景
用户设计了 ParserService（Docker服务），但 E2E 测试揭示关键问题：

| 方案 | 扫描PDF质量 | 测试结果 |
|------|------------|---------|
| Docling EasyOCR | 2/10（失败） | 7页→5 chunks (<5%) |
| MinerU API | 10/10（完美） | 34s, 4515字 |

设计文档假设 Docling OCR "质量3/5 Acceptable"，但实测证明根本失败。

### 决策结果
**选择方案A：直接用 MinerU API**

理由：扫描PDF质量实测差距过大（2/10 vs 10/10），放弃自建 ParserService。

## 2026-04-23: MindGarden 卡片生成架构（已决策）

### 背景
- 用户接受 Supabase + MinerU API 方案（放弃 ParserService）
- 需设计 Markdown → Anki Card 的创建管道
- 用户调研了 easy-dataset 项目，借鉴其方式但需优化成本

### 决策
采用 **Qwen全栈API架构**（无需本地部署）

### 技术选型
| 步骤 | 模型/API | 定价 | 理由 |
|------|---------|------|------|
| 文档解析 | MinerU API | 按文件计费 | 扫描PDF质量10/10（实测） |
| 预处理 | Qwen3.5-Flash | 0.2元/1M输入，2元/1M输出 | 极低成本，分类提取足够 |
| 卡片生成 | Qwen3.6-Flash | 1.2元/1M输入，7.2元/1M输出 | 推理更强，生成质量更高 |

### 架构流程
```
Markdown → MinerU API → 纯规则清洗 → Qwen3.5-Flash预处理 → Qwen3.6-Flash卡片生成 → Supabase存储
```

### 预处理任务（Qwen3.5-Flash）
- 知识点识别
- 类型分类（definition/concept/process/comparison）
- 关键词提取（3-5个）
- 难度初步评估（easy/medium/hard）

### 卡片生成任务（Qwen3.6-Flash）
- 基于预处理信息生成高质量问答卡片
- 问题简洁（10-25字）
- 答案精确（20-50字）
- 确认或修正难度

### 成本优势
- 对比 Easy Dataset模式（81次LLM调用/chunk）：**133倍降低**
- 对比 GPT全栈方案：**15倍降低**
- 100 chunks总成本：~1.5元 ≈ $0.21

### 部署方案
- Vercel 全栈部署
- 统一使用阿里云 DashScope API
- 单一密钥管理（DASHSCOPE_API_KEY）

### 决策理由
1. 云端API零运维 → 适合快速上线
2. Qwen3.5-Flash成本极低 → 预处理成本可忽略
3. Qwen3.6-Flash推理强 → 卡片质量有保障
4. 全流程线上 → 本地测试可模拟（Ollama）

### 风险与缓解
| 风险 | 缓解方案 |
|------|---------|
| 预处理准确率不足 | Qwen3.6-Flash可纠正难度 |
| API依赖第三方 | DashScope国内稳定，可备选其他 |
| Token消耗超预期 | 监控用量，必要时启用显式缓存 |

## 2026-04-23: MindGarden 产品定位决策 → Mind Garden

### 背景
- 已完成MindGarden后端架构设计（MinerU + Qwen全栈）
- 但产品缺乏情感价值，用户难以形成长期粘性
- 用户视角：MindGarden是"工具"，冷冰冰的卡片
- 需要：让用户喜欢用、有成就感、可感知成长

### 决策
将 MindGarden 重新定位为 **Mind Garden（思维花园）**

### 核心概念
用户上传文档 → 播下一颗种子 → 学习记忆 → 种子发芽→生长→含苞→盛开

| 里程碑 | 掌握度 | 植物形态 | 情绪价值 |
|--------|--------|---------|---------|
| 播种 | 0% | 种子落地 | 期待感 |
| 发芽 | 25% | 嫩芽破土 | 惊喜感 |
| 生长 | 50% | 茎叶生长 | 成就感 |
| 含苞 | 75% | 花苞出现 | 期待感 |
| 盛开 | 100% | 花朵完全盛开 | 自豪感+满足感 |

### 知识类型与植物形态

| 知识类型 | 植物形态 | 视觉特点 |
|---------|---------|---------|
| definition | 小白花 | 简洁清新 |
| concept | 兰花 | 优雅独特 |
| process | 向日葵 | 阳光向上 |
| comparison | 双色花 | 对比有趣 |
| fact | 小草花 | 朴实可爱 |

### 花园等级

| 等级 | 植物数量 | 名称 |
|------|---------|------|
| 1-5株 | 小花园 | 新手园丁 |
| 6-20株 | 大花园 | 业余园丁 |
| 21-50株 | 植物园 | 专业园丁 |
| 51-100株 | 国家公园 | 花园大师 |
| 100+株 | 世界花园 | 植物学家 |

### 情绪价值设计

**核心价值**：
- 成就感：花朵盛开时刻的视觉反馈
- 自豪感：花园全景展示学习历程
- 美学享受：不同植物形态的艺术设计
- 社交分享：截图分享花园炫耀成就
- 养育满足：看到知识从种子长成花朵

**用户选择Mind Garden的原因**：
不是因为"它功能强大"
而是因为"种下知识，看着它开花的感觉很美好"

### 核心价值金字塔

```
Level 1: 功能价值（底层）
├─ 高效记忆（SM-2算法）
├─ 智能调度
├─ 按章节分组
├─ 多种学习模式

Level 2: 体验价值（中层）
├─ 游戏化反馈
├─ 视觉化进度
├─ 里程碑动画
├─ 成就解锁

Level 3: 情绪价值（顶层）
├─ 成就感（花朵盛开）
├─ 自豪感（花园丰盛）
├─ 美学享受（植物形态）
├─ 社交分享（炫耀花园）
├─ 养育满足（看到知识成长）
```

1. 情感连接：Mind Garden比MindGarden更容易形成情感粘性
2. 记忆点：花朵盛开比数字统计更易记住
3. 成就感：视觉反馈比抽象统计更有成就感
4. 品牌调性：温暖美学比冷冰冰工具更吸引人
5. 长期价值：用户会因为"养育感"而持续使用

## 2026-04-23: Mind Garden 植物生成方案决策 → AI生成独一无二

### 背景
- 已确定Mind Garden产品定位（种子→盛开）
- 原设计：预设5种固定植物类型 × 5阶段 = 25种形态
- 问题：同类型知识库植物相同，缺乏独特性
- 用户无法参与创作，缺乏情感连接
- 无法承载"世界上所有植物"的愿景

### 决策
采用 **AI生成方案**：每个知识库生成独一无二的植物

### 核心创新

| 维度 | 预设方案 | AI生成方案 |
|------|---------|-----------|
| 植物种类 | 5种固定 | **无限多样性（世界所有植物）** |
| 独特性 | 同类型相同 | **每个知识库独一无二** |
| 用户参与 | 无参与 | **用户选择/描述→参与创作** |
| 生成方式 | 手工设计SVG | **文生图API生成关键帧** |
| 动画方式 | CSS预设动画 | **图生视频API生成3-5秒动画** |
| 成本 | 设计成本高 | **API调用¥0.5/植物（可控）** |
| 情感价值 | 固定视觉 | **创作感+独特感+期待感** |

### 完整流程

```
用户上传文档 → 文档处理等待期（30-60秒）
    ↓
交互："你想种下什么样的植物？"
    ├─ 用户输入植物描述（可选）
    ├─ 用户选择风格/颜色（可选）
    ├─ 系统自动创作（用户不指定时）
    ↓
Qwen3.6生成植物概念
    ├─ 植物名称："月光玫瑰"
    ├─ 植物描述："银蓝色玫瑰，神秘优雅"
    ├─ 关键词：月光、银蓝色、玫瑰
    ↓
文生图API生成5个关键帧
    ├─ seed.png（种子形态）
    ├─ sprout.png（发芽形态）
    ├─ growing.png（生长形态）
    ├─ budding.png（含苞形态）
    ├─ blooming.png（盛开形态）
    ↓
里程碑触发 → 图生视频API生成动画
    ├─ 25% → sprout_video.mp4（3-5秒）
    ├─ 50% → growing_video.mp4（3-5秒）
    ├─ 75% → budding_video.mp4（3-5秒）
    ├─ 100% → blooming_video.mp4（5-8秒）
    ↓
Artifacts完整存储（一致性保障）
    ├─ plants/{plant_id}/
    │   ├─ metadata.json
    │   ├─ keyframes/*.png
    │   ├─ videos/*.mp4
```

### 多模态API选型

**文生图API**：
| API | 定价 | 推荐 |
|------|------|------|
| Qwen-VL-Plus（阿里云） | ¥0.02/图 | **推荐（国内稳定）** |
| DALL-E 3（OpenAI） | $0.04/图 | 高端用户 |
| Stable Diffusion API | $0.02/图 | 成本敏感 |

**图生视频API**：
| API | 定价 | 推荐 |
|------|------|------|
| RunwayML Gen-2 | $0.05/秒 | 高端用户 |
| Pika Labs | Beta免费 | 免费期可用 |
| Stable Video Diffusion | $0.02/秒 | 成本敏感 |

**成本测算**：
- 文生图：5图 × ¥0.02 = ¥0.1
- 图生视频：4视频 × 5秒 × ¥0.02 = ¥0.4
- **总成本：¥0.5 ≈ $0.07/植物**

### 等待期交互设计

**核心洞察**：文档处理需30-60秒，利用等待时间引导用户创作植物

```
交互界面：
├─ 进度条："文档解析 80%"
├─ 提示："在等待期间，创作你的专属植物"
├─ 用户选择：

│   ├─ 选择颜色：白色/粉色/蓝色/紫色
│   ├─ 系统自动创作（用户不指定）
├─ 实时预览："植物名称：月光玫瑰 ✨"
├─ 用户确认："确定种下月光玫瑰"

```

### 核心价值

**用户选择Mind Garden的原因**：
- 不是因为"功能强大"
- 不是因为"漂亮花朵"
- 而是因为"我自己创作的月光玫瑰，看着它从种子长成盛开的花，这是我的专属"

**产品核心竞争力**：
- 每个用户的花园独一无二
- 每株植物有用户的故事
- 用户与植物情感连接深度
- 不可能被其他产品复制（每个植物都是AI生成的）

### 决策理由
1. 独特性：每个知识库植物独一无二 → 情感连接更深
2. 用户参与：等待期交互 → 创作感+参与感
3. 无限多样性：承载"世界所有植物"愿景 → 产品边界无限
4. 成本可控：¥0.5/植物 → API成本可接受
5. 不可复制：AI生成 → 其他产品无法抄袭

### 风险与缓解

| 风险 | 缓解方案 |
|------|---------|
| API调用失败 | Fallback到预设植物形态 |
| 图生视频延迟 | 关键帧一次性生成，视频按里程碑触发时才生成 |
| 成本超预期 | 监控用量，必要时启用缓存 |
| 用户描述模糊 | Qwen理解意图，优化生成结果 |
| API不稳定 | 多API备选（Qwen-VL、DALL-E、SD） |

1. 新增多模态API集成文档 → 文生图+图生视频技术方案
2. 实现植物创作交互界面 → 等待期用户参与

## 2026-04-23: Mind Garden API选型调整 + 场景生成优化

### 背景
- 已确定AI生成植物方案（文生图+图生视频）
- 原选型：Qwen-VL-Plus + Pika Labs
- 问题1：API需VPN或国内服务稳定性存疑
- 问题2：植物生成无场景背景，孤零零的盆栽感
- 用户需求：沉浸感更强的场景化植物成长

### 决策
调整API选型为 **豆包系列** + 新增 **场景生成优先** 流程

### API选型调整

| 维度 | 原方案（Qwen-VL + Pika） | 新方案（豆包Seedream + Seedance） |
|------|------------------------|-------------------------------|
| 文生图API | Qwen-VL-Plus（阿里云） | **豆包Seedream（字节跳动）** |
| 图生视频API | Pika Labs（国外） | **豆包Seedance（字节跳动）** |
| 国内可用 | ✅ Qwen-VL可用 | **✅ 豆包完全国内稳定** |
| VPN需求 | Pika需VPN | **❌ 无需VPN** |
| 中文理解 | Qwen-VL强 | **✅ 豆包更强（字节跳动）** |
| 技术支持 | 阿里云 | **字节跳动** |

**豆包API信息**：
- Seedream：文生图、图生图、Inpainting
- Seedance：图生视频、视频生成
- 官网：字节跳动豆包大模型平台
- 定价：待确认（预计与Qwen-VL相当）

### 场景生成优化

**核心改进**：先生成场景图，再在场景基础上生成植物关键帧

| 维度 | 原方案 | 新方案 |
|------|--------|--------|
| 关键帧生成 | 文生图直接生成植物 | **场景图 → 图生图生成植物** |
| 视觉效果 | 空白背景，孤零零植物 | **真实场景（花园/稻田）+ 植物生长** |
| 场景一致性 | 无场景概念 | **场景固定，植物位置固定** |
| 沉浸感 | 盆栽感 | **自然野区整体环境感** |
| 独特性 | 植物独特 | **植物在场景中独一无二** |

### 新流程设计

```
用户输入植物描述 → Qwen生成植物+场景Prompt
    ↓
豆包Seedream生成场景图
    ├─ Prompt："月光下的花园场景，银蓝色月光洒落，
    │           花园里有草坪、石头，右下角留空（植物将在此生长）"
    ├─ 输出：场景图（scene.png）
    ├─ 特点：
    │   ├─ 完整场景（月光花园）
    │   ├─ 其他元素（草坪、石头）
    │   ├─ 右下角留空（植物位置）
    ↓
豆包Seedream图生图生成关键帧（Inpainting）
    ├─ 输入：场景图 + 植物Prompt + Mask（右下角）
    ├─ 场景不变，右下角添加植物
    ├─ 输出5关键帧：
    │   ├─ seed.png（场景+种子）
    │   ├─ sprout.png（场景+嫩芽）
    │   ├─ growing.png（场景+生长）
    │   ├─ budding.png（场景+含苞）
    │   ├─ blooming.png（场景+盛开）
    ↓
豆包Seedance生成里程碑动画
    ├─ 输入：关键帧图片
    ├─ 场景不变，植物在固定位置成长
    ├─ 输出4视频（sprout.mp4等）
```

### Inpainting技术

**核心技术**：局部图像编辑，在场景固定位置添加植物

**提前生成逻辑**：

```javascript
// lib/plant/video-pre-generator.ts

export async function checkAndPreGenerateVideo(plantId: string, currentProgress: number) {
  const milestones = [25, 50, 75, 100];
  
  for (const milestone of milestones) {
    // 提前2%时静默生成
    const triggerThreshold = milestone - 2;  // 23%、48%、73%、98%
    
    if (currentProgress >= triggerThreshold && !isVideoGenerated(plantId, milestone)) {
      // 静默调用Seedance生成视频（用户无感知）
      await generateMilestoneVideoSilently(plantId, milestone);
      
      console.log(`Pre-generated ${milestone}% video for plant ${plantId}`);
    }
  }
}

async function generateMilestoneVideoSilently(plantId: string, milestone: number) {
  // 调用Seedance生成视频
  const video = await doubaoSeedance.generate({
    input_image: getKeyframeUrl(plantId, getPreviousStage(milestone)),
    target_image: getKeyframeUrl(plantId, getCurrentStage(milestone)),
    prompt: getVideoPrompt(plantId, milestone),
    duration: milestone === 100 ? 8 : 5
  });
  
  // 存储视频（但不立即播放）
  await storeMilestoneVideo(plantId, milestone, video.url);
  
  // 标记为已生成
  await markVideoAsGenerated(plantId, milestone);
}
```

```
  ├─ 用户看到成长过程 → 期待感
  ├─ 但不知道种下什么植物 → 惊喜感
  ├─ 可提供"返回主页"按钮（后台静默生成）
  ↓
解析完成 + 卡片生成完成 + 植物关键帧生成完成
  ↓
自动跳转到新知识库花园
  ↓
按钮逻辑变化（见下方）
```

### 按钮逻辑变化设计（关键设计）

**决策：最大化利用相同按钮，不同场景不同逻辑**

| 场景 | 左按钮 | 中按钮 | 右按钮 |
|------|--------|--------|--------|
| **主页花园** | 照相机（分享已完成知识库） | 空地（种下新知识） | 浇水壶（弹出知识库卡片） |
| **知识库花园** | 空地（返回主花园） | 浇水壶（继续学习） | 照相机（分享当前进度） |

**按钮逻辑变化触发时机**：
```
用户点击空地（主页）
  ↓
上传文档
  ↓
等待解析
  ↓
解析完成
  ↓
自动跳转到知识库花园
  ↓
按钮逻辑变化：
  ├─ 左：空地 → 返回主花园
  ├─ 中：浇水壶 → 继续学习
  ├─ 右：相机 → 分享当前进度（或分享当前画面）
```

**分享逻辑**：
```
主页花园的相机：
  ├─ 无已完成知识库 → 提醒："请先完成一个知识库"
  ├─ 有已完成知识库 → 弹出已完成列表 → 选择分享

知识库花园的相机：
  ├─ 进度<100% → 分享当前进度和当前画面
  ├─ 进度=100% → 分享纪念插画
```

```
  ├─ Step 3: 聚焦最终插画效果（场景+植物生长状态）
  ├─ Step 4: 场景可包含小动物（扩展功能）

场景想象力：

核心原则：
```

## 2026-04-23: 卡片生成策略设计决策 → 用户采集 + Prompt组装路由 + 小批量验证 + Prompt Cache

### 背景
- 已确定卡片生成使用Qwen3.6-Flash API
- 已确定Prompt管理模块（PromptTemplates + PromptAssembler + PromptRegistry）
- 问题：用户群体差异大（小学生到成人），学习目的不同（考试/考编/考证/语言学习）
- 问题：不同受众和目的需要不同的卡片内容、难度、题型、语言风格
- 问题：批量生成可能耗时30-60秒，如果结果不满意浪费用户时间
- 问题：同一份文档可能需要生成不同题型卡片（选择题/填空题/简答题）

### 决策
设计用户采集界面 + Prompt组装路由 + 小批量验证 + Prompt Cache：
1. **用户采集界面**：点击"生成卡片"按钮时弹出采集选项
2. **题型多选限制**：订阅等级限制题型数量
3. **Prompt组装路由**：根据用户选择路由到不同Prompt模板
4. **小批量验证**：先生成1-2题，用户确认后再批量
5. **调整策略次数**：订阅等级限制调整次数
6. **默认策略**：三类默认策略（学生考试/成人培训/语言学习）
7. **Prompt Cache**：保存用户策略，减少token消耗

### Prompt Cache设计

**Prompt Cache作用**：
| 作用 | 说明 |
|------|------|
| **减少Token消耗** | 同类型文档使用相同策略，无需重新组装Prompt |
| **快速响应** | Max用户优先使用Cache，响应更快 |
| **策略复用** | 下次同类型文档自动应用已保存策略 |

**Prompt Cache存储结构**：
```
数据库表：prompt_cache
├─ id: UUID
├─ user_id: UUID (FK)
├─ document_type: string (学科知识/职业知识/语言知识等)
├─ strategy_config: JSON {
│   ├─ identity: string
│   ├─ purpose: string
│   ├─ types: array
│   ├─ style: string
│   }
├─ assembled_prompt: text (组装后的完整Prompt)
├─ created_at: timestamp
├─ updated_at: timestamp
```

**Prompt Cache使用逻辑**：
```
用户上传新文档
  ↓
系统分析文档类型
  ↓
检查Prompt Cache：
├─ 有同类型文档的Cache → 自动应用已保存策略
│   ├─ 提示："已自动应用您之前保存的策略"
│   ├─ 用户可选择"使用保存的策略"或"重新选择策略"
│   │
├─ 无Cache → 弹出采集界面，用户手动选择
│   ├─ 用户选择策略后，提示"是否保存此策略？"
│   ├─ 用户选择保存 → 存入Prompt Cache
```

**订阅等级与Prompt Cache**：
| 用户类型 | Prompt Cache | 优先响应 |
|---------|-------------|---------|
| **Free** | ✅ 可保存Cache | 无优先 |
| **Pro** | ✅ 可保存Cache | 无优先 |
| **Max** | ✅ 可保存Cache | ✅ 优先使用Cache，响应更快 |

### 决策理由
1. **采集界面时机**：同一份文档可反复生成不同题型，适应不同考试方式
2. **题型多选限制**：降低Prompt组装复杂度，订阅等级差异化
3. **小批量验证**：避免用户等待长时间但结果不满意
4. **调整策略次数**：订阅等级差异化，Free有限调整，Max无上限
5. **默认策略**：用户未选择时，大模型自动路由到三类默认策略
6. **Prompt Cache**：减少Token消耗，快速响应，策略复用
